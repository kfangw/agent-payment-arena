# Repeated relationship evaluation

## Purpose

Specify the evaluation harness for repeated buyer-seller relationships in enough
detail that implementation does not require new modeling or statistical choices.
The harness measures when a buyer should pay, verify, defer payment, or end a
relationship with a seller whose behavior is not directly observable.

This experiment is separate from the settlement experiment. The settlement
experiment studies a server deciding whether to grant one payment under channel
delay and failure. This experiment studies a buyer making repeated payments to
one persistent seller while evidence changes the buyer's belief. The two
experiments may reuse infrastructure but must not import each other's model,
policy, or naming modules.

The implementation belongs in:

    src/arena/experiments/relationship/

Reusable execution, artifact, and statistical functions remain in:

    src/arena/experiments/artifacts.py
    src/arena/experiments/runner.py
    src/arena/experiments/statistics.py

No module, public type, command, artifact key, or test name may contain a paper
title, venue name, or submission label.

## Behavior

### Evaluation question

For a declared transaction model and seller response, the harness compares one
compiled deposit-and-exit policy with fixed and adaptive competitors. It reports:

1. buyer utility per completed transaction;
2. verification count and cost;
3. loss from cheated deliveries;
4. false exits against honest sellers;
5. transactions completed before a cheating seller exits;
6. seller cheating rate and deterrence slack;
7. deposit size and opportunity cost;
8. total surplus and computation cost.

One buyer-seller relationship is the independent sampling unit. Transactions
inside a relationship are observations on one path, not independent samples.
Every policy in a comparison cell replays the same exogenous relationship path.

### Protocol lock

The first implementation ships a checked-in resolved configuration:

    configs/relationship/protocol-0.3.1.yaml

The configuration has two versions:

- `schema_version` changes when the parser or field layout changes.
- `protocol_version` changes when an estimand, policy, cell, seed split, tuning
  rule, or decision threshold changes.

The runner writes both versions into every artifact. An evaluation run refuses
an uncommitted configuration by default. `--allow-dirty-config` is available for
pilot diagnostics and marks every resulting artifact `exploratory: true`.
Exploratory artifacts cannot be aggregated into confirmatory tables.

The initial protocol uses the following generated operating point:

| parameter | value | meaning |
|---|---:|---|
| `v` | 1.0 | prepaid transaction value |
| `u` | 0.2 | honest buyer surplus as a fraction of `v` |
| `alpha` | 0.02 | false-failure probability |
| `beta` | 0.10 | missed-cheating probability |
| `behavioral_cheat_rate` | 1.0 | cheating rate of a behavioral bad seller |
| `g` | 0.45 | seller's one-transaction gain from cheating |
| `deposit_cap` | 10.0 | maximum posted deposit |
| `prior_bad` | 0.05 | initial probability of a bad seller |
| `escrow_cost_rate` | 0.05 | cost of deferred payment as a fraction of `v` |
| `seller_margin` | 0.10 | honest per-transaction seller margin |

Verification-cost cells set `verification_cost` to `3v` and `1.2v`.
Relationship-length cells set `continuation_probability` to 0.80, 0.95, and
0.98, corresponding to expected lengths of 5, 20, and 50 transactions.

### Input provenance

Every input field carries one of three provenance grades in the resolved
configuration:

- `G`: generated by the harness;
- `P`: parameterized from an external report or study;
- `M`: measured from a declared data query.

The confirmatory suite uses grade `G`. A measured workload may affect only a
secondary operating-point analysis unless a later protocol version promotes it
before evaluation seeds are opened. Seller type, delivery quality, and predicate
error must never be labeled `M` merely because a settlement record exists.

## Model contract

### Public and latent types

`RelationshipObservation` is the only object visible to a policy:

    @dataclass(frozen=True)
    class RelationshipObservation:
        transaction_index: int
        belief_bad: float
        deposit: float
        pending_verdicts: int
        last_verdict: Verdict
        cumulative_public_checks: int
        cumulative_discretionary_checks: int

        cheating_uniforms: NDArray[float64]

The policy module must not import `LatentRelationship`. A structural test rejects

### Stable enums

The package defines experiment-specific enums to avoid collision with the
gateway's `Action`:

    class RelationshipAction(StrEnum):
        PAY = "pay"
        VERIFY = "verify"
        DEFER = "defer"
        EXIT = "exit"

    class Verdict(StrEnum):
        PASS = "pass"
        FAIL = "fail"
        NOT_CHECKED = "not_checked"
        PENDING = "pending"

    class SellerType(StrEnum):
        HONEST = "honest"
        BAD = "bad"

    class SellerMode(StrEnum):
        BEHAVIORAL = "behavioral"
        STRATEGIC = "strategic"

Serialized values are part of the artifact schema and cannot be renamed without
a schema-version change.

### Parameter validation

`RelationshipConfig` is an immutable Pydantic model. It rejects configurations
that violate:

    v > 0
    u > 0
    0 <= alpha < 1
    0 <= beta < 1
    1 - beta > alpha
    0 <= behavioral_cheat_rate <= 1
    g >= 0
    deposit_cap >= 0
    0 < prior_bad < 1
    escrow_cost_rate >= 0
    seller_margin >= 0
    verification_cost >= 0
    0 <= continuation_probability < 1
    max_transactions >= 1

The resolved configuration stores values in transaction-value units and never
depends on a display currency.

The loader uses `yaml.safe_load` and validates the resulting mapping with
Pydantic. YAML is required for the protocol, so PyYAML is a base runtime
dependency rather than an experiment-only optional dependency.

### Event order

The simulator uses this order for transaction `t`:

1. Deliver verdicts whose declared delay expires at the start of `t`.
2. Apply each delivered verdict to the belief in FIFO order.
3. If the relationship already exited, return without another transaction.
4. Give the resulting public observation to the buyer policy.
5. If the action is `exit`, record the exit and return.
6. The seller chooses delivery behavior without seeing the current public coin.
7. Execute the delivery and the payment timing implied by the action.
8. For `pay`, draw the public sampling coin. For `verify` and `defer`, check
   with probability one.
9. Draw a predicate verdict if a check occurs.
10. Apply an immediate verdict or enqueue a delayed verdict.
11. Apply payment, refund, deposit forfeiture, reposting, and verification cost.
12. Record one immutable transaction event.
13. Draw exogenous continuation. On failure, record departure and return.

The seller knows the announced sampling rate and deposit before the relationship.
It does not know the current public coin or predicate error before choosing the
delivery. The buyer does not observe delivery quality except through a verdict.

### Delivery and predicate

An honest seller delivers correctly. A behavioral bad seller cheats independently
with the configured rate. A strategic seller uses the response described below.

For a bad seller with cheating probability `phi`:

    p_fail_bad = phi * (1 - beta) + (1 - phi) * alpha
    p_fail_honest = alpha

The posterior after a failed check is:

    b_fail = b * p_fail_bad / (b * p_fail_bad + (1 - b) * alpha)

The posterior after a passed check is:

    b_pass =
        b * (1 - p_fail_bad)
        / (b * (1 - p_fail_bad) + (1 - b) * (1 - alpha))

No check leaves the belief unchanged. Implementations compute in log-odds space
when direct probabilities would underflow, clamp only after the mathematically
defined update, and test both endpoint limits.

### Actions and transfers

`pay` prepays and consumes the result. The public coin may invoke the predicate.
`verify` also prepays but always invokes the predicate. `defer` holds payment
until a predicate verdict: pass pays the seller, while fail refunds the
transaction. `exit` ends the relationship with normalized continuation payoff
zero.

On a checked failure after prepayment:

- the seller forfeits the posted deposit;
- the buyer receives `min(deposit, v)`;
- any amount above `v` is burned or sent to the declared protocol sink;
- the seller reposts the deposit before a later secured transaction.

The buyer must never receive both a transaction refund and the loss-compensation
transfer for the same deferred payment. A regression test treats that
double-credit convention as an intentional negative control.

### Base-model invariants

The simulator asserts the following invariants in debug and validation modes:

1. belief remains in [0, 1];
2. deposit remains in [0, deposit_cap];
3. no event follows exit or exogenous departure;
4. `not_checked` is the only verdict when no predicate ran;
5. each transaction has exactly one payment state;
6. each forfeiture references one earlier secured transaction;
7. a policy cannot access latent state or future random draws;
8. equal configuration and seed produce equal normalized artifacts.

## Policy contract

All policies implement:

    class RelationshipPolicy(Protocol):
        policy_id: str

        def reset(self, context: PolicyContext, rng: Generator) -> None: ...
        def act(self, observation: RelationshipObservation) -> RelationshipAction: ...
        def snapshot(self) -> Mapping[str, JsonValue]: ...

`reset` receives resolved public terms and a policy-specific random generator.
`snapshot` returns all compiled boundaries and tuned parameters. The runner writes
the snapshot before evaluation starts and hashes it into the run identifier.

Policies cannot mutate model configuration. They may keep private public-history
state only when that state is included in `snapshot` and deterministically reset.

### Tested policy

`compiled_deposit_exit` is built before an evaluation run:

1. compute feasible public sampling and deposit pairs from seller incentives;
2. select the pair that minimizes the declared design objective;
3. solve the buyer Bellman equation on the belief grid;
4. compare pay, verify, defer, and exit at each grid point;
5. extract connected action intervals and boundary values;
6. serialize a read-only policy snapshot.

The default belief grid spacing is 0.001. Value iteration stops when its sup-norm
residual is at most `1e-10`. The hard iteration limit is 100,000. Hitting the
limit, returning a nonfinite value, producing disconnected regions where the
configuration requires an interval, or disagreeing with an available analytic
boundary by more than two grid cells is a validation failure.

Policy interpolation uses linear value interpolation and a deterministic action
tie order:

    EXIT > DEFER > VERIFY > PAY

The conservative order prevents a numerical tie from silently moving money.
The tie order is part of the protocol and appears in the policy snapshot.

### C0: always pay

`always_pay` pays on every active transaction. It is a diagnostic extreme and
is not eligible to become the strongest confirmatory competitor.

### C1: always verify

`always_verify` prepays and forces a check on every active transaction. It is a
diagnostic extreme and is not eligible to become the strongest confirmatory
competitor.

### C2: belief-adaptive sampling

`adaptive_sampling` divides the posterior into low, middle, and high-risk
intervals and assigns a nondecreasing verification probability:

    boundary candidates: 0.01, 0.02, ..., 0.99
    rate candidates: 0, 0.01, 0.025, 0.05, 0.10, 0.20, 0.50, 1.00
    constraint: rate_low <= rate_middle <= rate_high

The action is `verify` with the selected probability and `pay` otherwise. Its
random generator is policy-specific and does not consume public-coin draws.
At or above the tested policy's locked exit boundary it exits. Sharing this
boundary makes C2 a strong comparison of the verification schedule without
giving its tuner access to another free stopping threshold.

### C3: Wald sequential test

`wald_sprt` accumulates verified log-likelihood increments. It retains the
relationship between two boundaries, stops checking and pays thereafter at the
good-seller boundary, and exits at the bad-seller boundary.
Candidate type-I and type-II targets are:

    0.001, 0.005, 0.01, 0.025, 0.05, 0.10

The report includes classical approximate boundaries and exact finite-lattice
operating characteristics. Policy selection and final reporting use the exact
values, not the approximation.

### C4 and C5: strike rules

`one_strike` exits after the first failed verdict. `two_strike` exits after the
second failed verdict. Both use the tested policy's public sampling rate in the
same cell. Neither has a tuned evaluation parameter.

### C6: no public sampling

`no_public_sampling` fixes the public rate at zero and resolves the buyer problem
with discretionary verification and exit. It isolates the effect of a public
commitment while keeping the information action available.

### C7: no deposit

`no_deposit_optimum` fixes the deposit at zero and resolves every other design
and buyer-policy variable. It isolates the deposit's effect without replacing
the tested policy with an arbitrary fixed rule.

### Protocol terms by policy

C0-C6 use the tested policy's compiled deposit in the matched cell. C7 alone
fixes the deposit to zero. The tested policy compiles its public rate and
deposit. C4 and C5 reuse those posted terms. C2 commits its state-dependent
sampling map and uses the same deposit. C3 verifies every transaction until one
of its boundaries is reached and uses the same deposit. C6 fixes the public
rate to zero but retains the deposit for a discretionary failed check. Every
posted term is included in the policy snapshot so a strategic seller responds
to the actual comparison policy.

### Tuning

Only C2 and C3 use tuning data. Candidate enumeration is stable and sorted.
The selected candidate maximizes tuning buyer utility. Candidates within
`1e-6` use these tie breakers in order:

1. fewer expected checks;
2. fewer boundaries;
3. lexicographically smaller serialized parameters.

The tuning command writes one immutable policy snapshot per cell. The evaluation
command accepts only those snapshots and has no code path that calls `tune`.

## Seller response

### Behavioral mode

The seller type is sampled once from `prior_bad`. An honest seller never cheats.
A bad seller cheats independently with `behavioral_cheat_rate`. The fixed type
persists until E3 explicitly enables type switching.

### Strategic mode

A strategic seller observes the public sampling rate, deposit, policy snapshot,
and exit rule before selecting a stationary cheating probability `phi` in [0, 1].
It does not observe future random draws.

The response compiler:

1. evaluates `phi = 0.00, 0.01, ..., 1.00`;
2. brackets the best grid point and its neighbors;
3. refines the bracket with golden-section search;
4. stops at interval width `1e-4`;
5. chooses the smaller `phi` when seller values differ by at most `1e-6`.

The objective includes honest margin, gain from cheating, false-positive
forfeiture, deposit reposting, and relationship loss after buyer exit. The
compiler writes the objective at every grid point, the refined optimum, and
deterrence slack. Evaluation loads this response snapshot and never optimizes
`phi` from evaluation paths.

## Experiments

### E0: mathematical and software verification

E0 runs before any performance comparison. It checks:

- Bayes updates against hand-computed cases;
- value iteration against the closed-form exit boundary;
- incentive constraints at and immediately below their boundary;
- connected action regions where required;
- finite-lattice failure and exit probabilities;
- Bellman residual and interpolation error;
- Monte Carlo values within three estimated standard errors;
- two negative payoff-convention controls that must fail.

E0 produces no policy-performance claim. Any failed E0 check blocks E1-E3.

### E1: primary comparison

E1 crosses:

    2 verification-cost points
    x 3 relationship lengths
    x 2 seller modes
    = 12 primary cells

Each cell evaluates the tested policy and C0-C7. The confirmatory contrast is
the tested policy minus the strongest eligible competitor among C2-C5. The
competitor is selected on tuning seeds and locked before evaluation.

### E2: component and capital sensitivity

E2 compares the tested policy with C6 and C7. It also disables belief-based exit
while retaining posted terms. A deposit-cap sweep evaluates:

    0.0, 0.5, 1.0, ..., 10.0

The report includes feasibility, selected sampling rate, seller participation,
and deterrence slack. E2 estimates the effect of each component; it does not
present the audit-times-penalty incentive inequality as a new empirical result.

### E3: assumption violations

E3 changes one feature at a time while compiling the buyer policy from nominal
parameters.

`type_switch_probability` takes 0.01, 0.05, and 0.10. The latent type flips with
that probability before each seller decision. The buyer continues to apply the
fixed-type posterior update.

`verdict_delay` takes 1, 3, and 5 transactions. One deposit is locked by the
oldest pending secured transaction. Later transactions may proceed without
additional secured coverage until the verdict arrives. A failed verdict
forfeits the available deposit once. This convention exposes the bounded-
exposure assumption instead of pretending one deposit secures unlimited
concurrent transactions.

`partial_delivery_fraction` takes 0.25, 0.50, and 0.75. On a cheating delivery
the buyer receives that fraction of the promised gross value, so its precheck
payoff is `(fraction * (1 + u) - 1) * v`. The seller's incremental cheating gain
is `(1 - fraction) * g`. The nominal policy assumes zero delivery.

`verification_error_multiplier` takes 0.50, 0.75, 1.25, 1.50, and 2.00.
Separate subexperiments multiply true `alpha` and true `beta`, clipping only at
one, while the compiled policy retains nominal rates.

E3 reports utility loss relative to the matched nominal cell, false-exit change,
and change in transactions completed before a bad seller exits.

## Randomness and split isolation

The generator is NumPy `PCG64DXSM`. A root `SeedSequence` creates named child
streams. Stream identifiers are declared integer constants, not Python hashes:

| stream | id |
|---|---:|
| seller type and type switching | 10 |
| cheating decisions | 20 |
| predicate errors | 30 |
| public sampling coin | 40 |
| exogenous continuation | 50 |
| partial delivery | 60 |
| policy-private randomization | 1000 + stable policy id |
| statistical resampling | 2000 |

The stable policy id is a checked-in integer map. Adding a policy appends an id;
existing ids never change.

`RelationshipKey` consists of protocol version, experiment, cell, phase, seed,
and relationship index. All policies in one key receive the same exogenous
streams. Policy-private streams are independent and cannot shift exogenous
draws. Changing policy iteration order must not change any policy result.

The fixed splits are:

| phase | seeds | relationships per seed and cell | permitted use |
|---|---:|---:|---|
| pilot | 1000-1029 | 500 | defects and resource estimates |
| tuning | 10000-10049 | 1,000 | C2 and C3 selection |
| evaluation | 20000-20099 | 2,000 | confirmatory and estimation results |

`SplitGuard` validates every requested seed. Importing evaluation seed constants
from `tune.py` is prohibited by a structural test. Pilot or tuning rows in an
evaluation artifact are a hard aggregation error.

The generated horizon is large enough that the probability of remaining active
at the cap is at most `1e-8` for each relationship-length cell. Active paths at
the cap are right-censored for exit-time metrics and counted in
`horizon_censored_relationships`.

## Metrics

### Primary estimand

The continuation draw is the sole implementation of geometric discounting.
Utilities must not also be multiplied by `gamma ** t` after a path has been
geometrically stopped.

For seed `r` and policy `p`:

    utility_per_transaction[r, p] =
        sum_relationships(total_buyer_utility)
        / sum_relationships(realized_transactions)

The primary cell effect is the mean paired seed difference between the tested
policy and the locked competitor. Relationships are generated independently
inside each seed, and no transaction is treated as its own sampling unit. The
seed is the stored reporting block. This ratio-of-sums avoids giving a
one-transaction relationship the same transaction weight as a 50-transaction
relationship while preserving within-relationship dependence.

A zero denominator is a failed seed, not a zero-valued observation. The runner
records the cause and aggregation stops.

### Secondary metrics

Each relationship summary contains:

- total buyer utility;
- realized transactions;
- public and discretionary check counts;
- verification and escrow costs;
- cheated-delivery loss;
- exit time and exit cause;
- false exit against an honest seller;
- bad seller active at departure or horizon;
- seller cheating count and realized rate;
- deposit and opportunity cost;
- seller utility and total surplus;
- pending verdict count at exit;
- simulation and policy-solve time.

Every mean report includes its denominator and count. Time-to-exit reports
right-censoring separately and do not encode censoring as an exit at the horizon.

## Inference

Policy effects are paired within `RelationshipKey`. For each seed, the harness
stores policy totals and the paired contrast needed to reconstruct the ratio
difference.

The primary report:

1. computes one ratio per policy from all complete relationships in each seed;
2. forms 100 paired seed-level differences for every E1 cell;
3. resamples those complete paired seed blocks 10,000 times;
4. produces two-sided simultaneous 95 percent intervals over the 12 E1 cells;
5. uses Bonferroni level `1 - 0.05 / 12` for each primary interval;
6. reports a paired sign-flip sensitivity test over seeds;
7. adjusts sensitivity p-values with Holm's method.

The practical-equivalence margin is `0.01 * u * v`, equal to 0.002 at the
canonical point.

Classification uses the simultaneous interval:

- `superior` when the lower bound is above the positive margin;
- `inferior` when the upper bound is below the negative margin;
- `equivalent` when the whole interval lies inside both margins;
- `undetermined` otherwise.

The existing `classify_interval` helper tests superiority against zero and
therefore cannot be reused unchanged for this classification. Add a separate
margin-aware helper with explicit tests rather than silently changing current
frontier and settlement semantics.

E2 and E3 are estimation analyses. They report paired intervals and raw effects
without a binary pass rule. No unregistered subgroup may appear in the primary
table.

### Manifest and atomicity

Every file is written to a temporary path in its destination directory, flushed,
and atomically renamed. `MANIFEST.sha256` is written last and covers every other
artifact by relative path. A directory without a valid manifest is incomplete
and cannot be aggregated.

The aggregate records every included run id and manifest digest. Report tables
are generated from relationship summaries, never copied from console output.

## Validation and tests

### Unit tests

- Bayes updates match hand calculations and endpoint limits.
- Action payoffs match type-conditional decompositions.
- Deposit refund and forfeiture are not double counted.
- Exit prevents all future events and utility.
- Delayed verdicts apply once and in FIFO order.
- Value iteration reaches the declared residual.
- Exact lattice recursion matches small enumerated trees.
- Bonferroni level, Holm adjustment, and sign-flip p-values match fixtures.
- Margin classification tests against the practical margin, not zero.

### Property tests

- More failed evidence never lowers the posterior bad probability.
- More passed evidence never raises it.
- Increasing the deposit cap does not increase the minimum feasible public rate.
- Equal configuration and seed produce byte-equivalent normalized output.
- Reordering policies does not change any policy's output.
- Chunk size and worker count do not change numerical results.
- No policy field, import, or method receives latent state.
- Pilot and tuning seeds cannot enter evaluation output.

### Regression tests

A small checked-in fixture stores:

- compiled boundaries on a 101-point belief grid;
- five complete relationship paths;
- strategic seller objectives at eleven `phi` values;
- seed-level metrics for two policies;
- aggregate summary and manifest hashes.

Floating-point values use named tolerances. JSON is canonicalized before
comparison. Platform-dependent timestamps and paths are excluded from the
fixture hash.

## Reference gateway integration

The main experiments remain offline. They do not need a wallet, chain, HTTP
server, or language model.

An optional contract test maps relationship events to the gateway revision
already pinned by this repository:

    stablecoin-x402-gateway ddd20fe3ec7c2109a006e1112bcac9fdeabf9b32

The adapter verifies transaction identifiers, amounts, decision values, deferred
states, bond requirements, and refund or rejection outcomes. It must reuse
`HttpGateway` and the differential-test fixture. It must not duplicate the
gateway's settlement implementation in Python.

The gateway action space and `RelationshipAction` are not identical. The adapter
performs an explicit mapping and rejects unsupported states. An integration
failure is a contract result, not a simulated policy-performance observation,
and never enters E1-E3 metrics.

## Failure handling and resumability

Independent cell-seed runs are immutable jobs. The batch runner skips only a
directory with a valid manifest and matching identity. It reruns incomplete
directories into a new quarantine path and never repairs them in place.

An invariant failure writes:

- the resolved configuration;
- policy snapshot;
- relationship key;
- public observations up to failure;
- generated latent draws required to replay the failure;
- exception type and stack trace.

Confirmatory aggregation fails closed on a missing cell, duplicate run identity,
mixed protocol version, mixed policy hash, unexpected seed, nonfinite metric, or
invalid manifest. It never silently drops a row.

Parallel jobs set numerical libraries to one thread through the shared runner.
Simulation is chunked by relationships. Chunk boundaries cannot affect random
streams or reductions. Seed-level totals use pairwise or compensated summation
and are merged in stable relationship-id order.

## Design decisions

### Geometric departure is the discount mechanism

The model parameter called `continuation_probability` is an exogenous survival
probability. Sampling departure already implements geometric discounting in
expectation. Applying `gamma ** t` again to a realized stopped path would count
the same mechanism twice. The primary implementation therefore uses undiscounted
realized utility before forming the seed-level ratio.

### Public and discretionary checks use separate random streams

The public coin is visible in the announced contract and affects seller
incentives. Discretionary checks are selected by a buyer policy under its current
belief. Giving both the same stream would make a policy's private decision shift
future public events and destroy the paired comparison.

### Tuning is physically absent from evaluation

Using separate seed ranges is not enough if the evaluation command can call a
tuner. Locked snapshots and a dependency-direction test make the separation a
software property rather than a convention.

### Relationship summaries are mandatory; event traces are diagnostic

The primary matrix produces millions of policy-relationship rows. Keeping every
transaction would multiply storage without changing the estimand. Relationship
summaries preserve the independent unit, while selected replay traces retain
debuggability.

### New code extends generic infrastructure

Artifact creation, block resampling, process execution, and log management are
already generic. The new package adds model-specific adapters and extends shared
functions only where the required semantics differ. It does not fork the
settlement package or add another parallel harness.

### The live gateway is a contract check

The gateway establishes whether abstract events map to a real API. It does not
provide seller ground truth or make stochastic performance estimates more valid.
Keeping the check separate preserves both claims.

## Limits

The base model assumes one persistent binary seller type, stationary cheating,
an informative binary predicate, an exogenous transaction opportunity rate, and
an immediate verdict. E3 measures selected violations but does not make the
closed-form policy valid outside those assumptions.

A deposit requires identity, capital, enforceable forfeiture, and a trusted
adjudication path. The harness measures the policy conditional on those
capabilities; it does not create them.

Generated seller types and predicate errors are not observations of production
fraud. A grade-M workload can ground relationship sizes and timing, but it cannot
turn latent generated outcomes into measured outcomes.

The strategic seller chooses a stationary scalar cheating probability. A seller
that conditions on full public history or coordinates identities requires a
larger game state and a new protocol version.

The finite grid validates the declared model, not every parameter combination.
Disconnected policy regions or failure of the monotonicity conditions are
reported as scope violations rather than smoothed away.

## Implementation sequence

The implementation should land as one pull request with reviewable commits:

1. Add the configuration schema, stable enums, and split guard.
2. Add belief updates, event records, and the single-relationship simulator.
3. Add value iteration, lattice recursion, and analytic E0 checks.
4. Add the tested policy and deterministic policy snapshots.
5. Add C0-C7 and tuning restricted to C2-C3.
6. Add behavioral and strategic seller responses.
7. Add E0-E3 cell generation and common-random-number batching.
8. Add metrics, margin-aware inference, and artifact manifests.
9. Add CLI commands, reports, gateway contract mapping, and documentation.

Every commit includes its direct unit tests. The final commit runs the reduced
smoke matrix. Full confirmatory results are generated after review and are not
committed in the implementation pull request.
